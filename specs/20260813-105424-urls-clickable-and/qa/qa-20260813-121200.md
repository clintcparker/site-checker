**Verdict**: ✅ ALL PASSED *(second run, after fixing the two failures the first run found)*

## QA Summary

Two QA passes were run. The **first** exercised all twelve functional requirements and six success criteria and found **two real failures**, both against FR-007's second sentence ("A URL that is not opened MUST NOT be presented as activatable") and one of them also against SC-002 ("100% of listed sites with an http or https address can be opened"). Both were confirmed empirically rather than inferred: a whitespace-padded stored address was rendered as an activatable control, accepted by the backend guard, and then handed to `/usr/bin/open` still padded — which macOS resolves as a **file path**, so it could never open and failed with a message naming a path the user has never seen. Separately, four hostless or malformed `http(s)://` addresses were rendered as controls and refused by the backend.

Per the run instructions the failing scenarios were **fixed and QA re-run exactly once**. The fixes were: `openable_url` now returns the trimmed address (so what is validated is what is opened), and `isOpenable` now asks the platform URL parser for a non-empty host and rejects a `%`- or whitespace-bearing host. That second guard needed a correction found *during* the re-run: a `host !== ""` test alone passes in happy-dom (which throws) and fails in Chromium (whose forgiving host parser percent-encodes `https://exa mple.com` into `exa%20mple.com` and reports success), so the first attempt produced a test that went green in CI while the real webview still rendered a dead control. Deciding the `%`/whitespace question in the guard itself makes the answer identical in every engine — which matters because the app ships in WKWebView, neither of the two engines it is tested in.

The second run reproduces every previously-failing case as fixed, with no regression in the other eighteen scenarios. All four quality gates are green (`cargo test` 101, `pnpm test` 80, `cargo clippy --all-targets -D warnings` clean, `tsc --noEmit` clean). The user's real `sites.json` was byte-identical before and after both passes.

**What could not be exercised, and why.** Accessibility was refused to this run — `AXIsProcessTrusted()` returns false even from a compiled Swift binary, System Events window calls fail `-25211`, synthetic keystrokes fail `1002` — and Screen Recording, which the *before* screenshots pass did have, is also refused now (`screencapture -R`/`-l` fail outright and a full-screen grab returns black). The Tauri window itself therefore could not be clicked, typed into, or photographed. Every interaction below was instead performed against the **shipped `render.ts` and `open.ts` modules loaded from the project's own Vite dev server into a real browser engine**, with only the Tauri IPC boundary stubbed to record calls. That covers real computed CSS, real `Tab`/`Enter` key presses, real `:focus-visible`, and real event dispatch; it does not cover WKWebView-specific rendering or the actual browser coming forward on screen. Those two gaps are named per-scenario below rather than waved at.

## Partial Results

### TC-218 — SC-003: "the browser comes forward within two seconds"

**Status**: ⚠️ PARTIAL — the app's own half is measured and well inside budget; the visible outcome is not observable in this environment.

**What was verified.** `/usr/bin/open <https url>` — the exact call `open_url` makes — was run four times against a real address and returned exit 0 in **33 ms, 48 ms, 62 ms and 67 ms**, ~30× inside SC-003's two-second budget. LaunchServices resolves a handler for both `http` and `https` (TC-217). The four opens produced new Firefox content processes, so the address was genuinely routed and loaded, not merely accepted.

**What was not.** The *frontmost* application stayed `Terminal` at 0.5 s, 1.2 s, 1.9 s and 2.6 s after the open. Whether that is this machine's URL router (Finicky is the registered handler and routes onward per its own config) declining to steal focus, or macOS's focus-stealing prevention for a background-launched process, could not be determined: window-level Accessibility is refused (`-25211`) and Screen Recording is refused, so neither the AX tree nor a screenshot could confirm which window is in front. The named remaining gap is therefore **visible browser activation only** — the dispatch, the latency, and the load are all confirmed.

### Screenshot evidence — what it is and is not

Both pairs of images in `qa/screenshots/` are the shipped `render.ts` + `styles.css` rendered by **Chromium at 720×480**, not the Tauri window. They are real post-change evidence of the affordance, the inert rendering and the focus ring; they are not evidence about WKWebView's rendering. The `screenshots/` extension's before pass (`../screenshots/manifest.json`) captured the real Tauri window, but it captured the **base tree** — it is cited here only for drivability history and unchanged-behaviour comparison, never as an observation of post-change behaviour. That manifest records `capture_blocked` nowhere and instead documents a VIEWPORT GAP and a STATE GAP: it says explicitly that hover and keyboard-focus states were **not** captured and that the app was **not** driven — no synthetic click, keystroke or resize succeeded in that run either. Its request that the after run "re-probe rather than assume" was honoured: `AXIsProcessTrusted()` was re-tested from a freshly compiled Swift binary and returned false again, and Screen Recording has additionally been lost since that run.

## Failure Details

### TC-104 / TC-201: a whitespace-padded address is offered, accepted, and never opens

**Status**: ❌ FAIL (first pass) → ✅ fixed and re-verified as TC-301
**Severity**: Medium — no crash, no data loss, fails safe into the banner, but it breaks a stated success criterion and the message misleads.

**Steps to Reproduce**:
1. Quit the app and hand-edit `sites.json` so an entry reads `"url": "  https://example.com  "`.
2. Relaunch. The row's URL renders underlined and activatable (`isOpenable` trims before testing).
3. Click it.

**Expected**: the default browser opens `https://example.com` (SC-002: 100% of http/https addresses open). Or, if it will not be opened, it is not offered as activatable (FR-007, second sentence).
**Actual**: `openable_url` validated `trimmed` but returned `input`, so `/usr/bin/open` received the padding. macOS resolves a leading-space argument as a **file path**, not a URL — verified directly:

```
$ /usr/bin/open "x-qa-nonexistent-scheme-zz://foo"
No application knows how to open URL x-qa-nonexistent-scheme-zz://foo (…kLSApplicationNotFoundErr…)

$ /usr/bin/open "  x-qa-nonexistent-scheme-zz://foo  "
The file /Users/clint/src/…/  x-qa-nonexistent-scheme-zz:/foo   does not exist.
```

So the address never opens, and the banner names a filesystem path the user has never seen. This also falsified the comment at `commands.rs:163` ("starts with `http` or `https` by the guard above").

**Evidence**: [responses/rust-openable-url-probe.txt](responses/rust-openable-url-probe.txt) (`OK returned="  https://example.com  "`), and the two `open` invocations above.

**Fix applied**: `openable_url` returns `trimmed.to_string()`. Surrounding whitespace is the only thing dropped and that is not a repair of the address — the WHATWG parser strips it anyway, `url::Url::parse` was already only ever handed `trimmed`, and `isOpenable` trims before deciding. What the guard returns is now, by construction, what is handed to `open`. Documented in `contracts/open-url-command.md`, `capabilities/backend/spec.md`, and the function's own doc comment; regression test `openable_url_returns_a_padded_address_without_its_padding` covers the padded, leading-space and trailing-newline forms.

### TC-213: addresses the UI offers that the backend refuses

**Status**: ❌ FAIL (first pass) → ✅ fixed and re-verified as TC-304
**Severity**: Medium — fails safe into the banner (nothing is spawned), but it is exactly what FR-007's second sentence forbids.

**Steps to Reproduce**:
1. Hand-edit `sites.json` to contain `https://`, `http://`, `https://[bad`, or `https://exa mple.com`.
2. Relaunch and look at the row.

**Expected**: not presented as activatable (FR-007).
**Actual**: all four satisfied `isOpenable`'s `^https?://` prefix test, rendered as underlined `<button>`s with `cursor: pointer`, and were all refused by `openable_url`. Confirmed in a real engine — the first-pass screenshot [fr004-fr007-affordance.png](screenshots/fr004-fr007-affordance.png) shows `https://` and `https://exa mple.com` underlined alongside the valid rows.

**Fix applied**: `isOpenable` now parses with the platform `URL` and requires a non-empty host, plus a host free of `%` and whitespace.

**A correction found during the re-run, worth recording.** The first version of this fix was `new URL(trimmed).host !== ""`, and its unit test passed — because happy-dom *throws* on `https://exa mple.com`. Chromium does not: its forgiving host parser percent-encodes the space and reports host `exa%20mple.com`, so the re-run's browser leg still showed that one row as an offered control while `pnpm test` was green. A guard that delegates its whole verdict to `URL` gives an engine-dependent answer, and this app ships in **WKWebView** — neither of the two engines it is tested in. Rejecting `%` and whitespace *in the parsed host* decides the question in the guard, identically everywhere, and deliberately looks at the host rather than the whole string so a legitimate space in a **path** (`https://example.com/a b`, which the add form accepts and the backend opens) is left alone. Tests now assert the Chromium-shaped input (`https://exa%20mple.com`) as well as the raw one, and assert the path-space case stays openable.
