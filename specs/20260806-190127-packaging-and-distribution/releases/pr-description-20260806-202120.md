## Implementation

**Three version numbers became one, and it is machine-written.** `tauri.conf.json`'s `version`
key is *deleted* rather than synchronised, so Tauri falls back to `Cargo.toml`. `Cargo.toml` and
`package.json` hold an inert `0.0.0` sentinel that `release.yml` stamps from the tag, and a CI
step fails any PR that edits either one. This was proven by building a stamped `9.9.9` and reading
`CFBundleShortVersionString` back out of `Info.plist` — not by trusting the documentation.

**`.github/workflows/release.yml`** — `preflight` → `test` → two-arch `build` matrix → `release` →
`homebrew`. Every job reaches `preflight` through its `needs:` chain, so a malformed tag or a
missing credential fails in seconds having built nothing, published nothing, and left the tap
untouched. `build` carries `preflight` as a *direct* need (GitHub's `needs` context exposes only
direct dependencies) — without that the stamp step would have written `version = ""`. The tap is
rendered from checksums of the assets **actually attached to the release**, never from predicted
names, with per-arch exact download patterns so a missing asset fails rather than silently
rendering one.

**`.github/workflows/ci.yml`** — the four gates the constitution names by hand now run on every
push to `main` and every pull request. This repository previously had no CI at all; three prior
ship runs stayed green through discipline, not enforcement.

**`.github/workflows/verify-install-channels.yml`** — daily, after every release, and on demand.
Catches the one failure a green release cannot: maintainer sees success, user sees a broken install.

**`install/homebrew/site-checker.rb`** — a cask, not a formula, because Site Checker ships an app
bundle. The advertised install line is identical either way, since Homebrew resolves a
tap-qualified name against both directories. This introduces the first mechanism in the project's
history that can delete the user's site list, and it is opt-in by construction: the data directory
appears in **exactly one stanza** and it is `zap`. `uninstall` carries `quit:` alone.

**`bundle.targets` is `["app"]`.** Building a DMG calls `osascript` against the Finder, which
blocks forever with no interactive session. Reducing the default means a build that forgets
`--bundles app` still cannot reach it — belt and braces. `pnpm tauri build --bundles dmg` still
works locally.

**[`docs/how-to/release.md`](https://github.com/clintcparker/site-checker/blob/b95ebc8dc9e7bbe6b6bb39db41cad151db5f3426/docs/how-to/release.md)** —
procedure, the seven-secret checklist, recovery, and the pre-flight's honest limit ("presence ≠
validity"). Committing it required un-ignoring `docs/how-to/` specifically as `docs/*` plus
`!docs/how-to/`; git will not re-include a file whose parent directory is excluded, so the exact
shape is load-bearing.

### Warnings (should fix)

| ID | File | Finding |
|---|---|---|
| **R001** / TC-027 | `verify-install-channels.yml:44–74` | **Highest-value item on this list.** Daily verification cannot detect **checksum** drift. It HEADs the asset URLs (reachability only) and greps the cask's `version`; it never compares the cask's two `sha256` values against the bytes attached to the release. Per research R14 a re-run uploads *different* bytes for the same tag, so a run where `release` succeeds and `homebrew` fails (an expired `TAP_PUSH_TOKEN` is the documented example) leaves a tap whose version and URL are both correct and whose checksums are stale — verification green, `brew install` aborting on a SHA256 mismatch. This is precisely the "green release, broken install" state US4 exists to catch. Fix: `curl -sfL` both assets, `sha256sum`, `grep -qF` each digest in the cask (~6 lines). |
| **R003** / TC-028 | `verify-install-channels.yml:11–13, 81–84` | `workflow_run: types: [completed]` has no `conclusion == 'success'` filter, and `e2e`'s only guard is `!= 'schedule'`. A Release run that dies at `test` or `build` still triggers `verify` (which passes against the *previous* release) and therefore `e2e` — a full `macos-latest` `brew install` + Gatekeeper check re-verifying a release nothing touched, billed at the 10× private-repo multiplier. One-line fix. |
| **R002** / TC-023 | `verify-install-channels.yml:61–74` | The post-release tap check reads `raw.githubusercontent.com`, which **is** CDN-cached — measured live during both review and QA: `cache-control: max-age=300`, `via: 1.1 varnish`. `workflow_run` fires seconds after `homebrew` pushes, so this step can read a cask up to ~5 min stale and fail a perfectly good release. **Research R12 dropped a retry loop on the stated grounds that raw "is available essentially immediately" — that premise is measurably wrong and should be corrected in place**, or the next person will repeat the reasoning. Exposure is bounded: it needs a prior request to have primed the same POP, which the daily cron does once a day. |
| **R004** / TC-029 | `release.yml:148–176` | 🔒 The Developer ID `.p12` is imported into an unlocked keychain with a `codesign`-permitting partition list, and the App Store Connect `.p8` is written to `$RUNNER_TEMP`, **before** `pnpm install --frozen-lockfile` runs npm lifecycle scripts. A compromised dependency would run with a usable signing identity already on the machine. Fix: move `Install frontend dependencies` above both credential steps. Zero cost, no behaviour change. Not reachable today — no credentials exist. |
| **R005** / TC-030 | `release.yml:16–17` | 🔒 `permissions: contents: write` is file-scoped, so `test` and `build` also get a write-capable `GITHUB_TOKEN`, which `actions/checkout@v4` persists into `.git/config` by default — in the same jobs that run third-party build tooling. Only `release` and `homebrew` need write. Fix: file-scope `contents: read` + job-level `write`, or `persist-credentials: false` on the `test`/`build` checkouts. |
| **R006** / TC-005 | `install/homebrew/site-checker.rb`, `release.yml:257–283` | **T017 is still open**: `brew audit --cask --new` has never run against a rendered cask, because Homebrew on the dev machine is broken (`brew config` aborts in the vendored `json-2.21.1` gem — an interrupted vendored-gem install during T017 itself).
