## Summary

The first non-CI install of `v1.0.0`. CI had already machine-checked quarantine
absence, `codesign --verify`, `Signature=adhoc`, the `bin` wrapper, and
`CFBundleShortVersionString` on a clean runner. What it could not check —
**that macOS opens a non-quarantined ad-hoc-signed app with no security
dialog** — is now observed rather than reasoned about. It does. The premise the
entire formula-over-cask design rests on holds.

Two things the install surfaced that no runner would have: the autostart
LaunchAgent hardcodes a version-pinned Cellar path, and the tap is `Untrusted`
under Homebrew's new tap-trust regime. Both are recorded below and tracked
separately.

### Machine

An Apple Silicon Mac that had **never built this project**: no
`src-tauri/target/release/`, no bundle ever produced locally, no
`/Applications/Site Checker.app`, tap not tapped, formula not installed.
Gatekeeper had therefore never seen this code signature.

*Honest caveat*: this is the author's daily-driver Mac with the repository
cloned and `cargo` debug artifacts present, not a pristine second machine. No
release bundle had ever existed on it, which is the property that matters for
the Gatekeeper and quarantine claims. It is not a fresh-user-account run.

## The artifact worth keeping

`spctl` output is not obtainable — an ad-hoc signature cannot pass
`spctl -a -t exec`, a recorded accepted loss (see
[docs/how-to/release.md](../../../docs/how-to/release.md)). `codesign -dv`
replaces it, as [#16](https://github.com/clintcparker/site-checker/issues/16)
directs.

```
$ codesign -dv --verbose=2 "/opt/homebrew/opt/site-checker/libexec/Site Checker.app"
Executable=/opt/homebrew/Cellar/site-checker/1.0.0/libexec/Site Checker.app/Contents/MacOS/site-checker
Identifier=com.clintparker.site-checker
Format=app bundle with Mach-O thin (arm64)
CodeDirectory v=20400 size=29813 flags=0x2(adhoc) hashes=925+3 location=embedded
Signature=adhoc
Info.plist entries=14
TeamIdentifier=not set
Sealed Resources version=2 rules=13 files=1
Internal requirements count=0 size=12
```

```
$ codesign --verify --strict --verbose=2 "/opt/homebrew/opt/site-checker/libexec/Site Checker.app"
/opt/homebrew/opt/site-checker/libexec/Site Checker.app: valid on disk
/opt/homebrew/opt/site-checker/libexec/Site Checker.app: satisfies its Designated Requirement
```

```
$ spctl -a -t exec -vv "/opt/homebrew/opt/site-checker/libexec/Site Checker.app"
/opt/homebrew/opt/site-checker/libexec/Site Checker.app: rejected
```

`rejected` is the **expected and accepted** result, not a regression. It is why
FR-021 was amended to `codesign --verify`. It is recorded here so that a future
reader who runs `spctl` and panics finds this line first.

### SC-002 — the load-bearing one

The claim that a non-quarantined ad-hoc-signed app opens without complaint was,
until now, macOS behaviour asserted by documentation and never observed. It is
now observed, by a human, twice:

1. Via the `site-checker` command on `PATH`. Window on screen in ~4.6s,
   app frontmost, **no dialog**.
2. Via `/Applications/Site Checker.app` — the symlink — which is the same
   LaunchServices path a Finder double-click takes. **No dialog.**

Supporting machine evidence, collected because a screenshot was unavailable
(the capturing process lacked Screen Recording permission):

- `log show --last 30m --predicate 'subsystem == "com.apple.syspolicy"'` —
  **no entries** mentioning `site-checker` or `clintparker`. Gatekeeper never
  assessed the app, because there was no quarantine flag to trigger assessment.
- `log show --predicate 'process == "CoreServicesUIAgent"'` — **no activity**.
  `CoreServicesUIAgent` is the process that draws the "unidentified developer"
  alert. It drew nothing.
- The app process was frontmost after launch. Had Gatekeeper blocked it, the
  alert would have been frontmost and the app would not be running.

**The channel is right.** Formula-over-cask does what
[docs/how-to/release.md](../../../docs/how-to/release.md) says it does.

### The `/Applications` symlink, including its honest half

```
$ ln -s "$(brew --prefix site-checker)/libexec/Site Checker.app" /Applications/
$ readlink "/Applications/Site Checker.app"
/opt/homebrew/opt/site-checker/libexec/Site Checker.app
```

Resolves through `opt/`, not `Cellar/1.0.0/`, so it survives upgrades — as the
README and the formula `caveats` both claim. Launching through it works.

The negative half the README promises is also true: `mdfind -name "Site
Checker.app"` and `mdfind -onlyin /Applications "Site Checker"` both return
nothing. Spotlight does not index an app through a symlink. `lsregister` *does*
know the bundle, but registered at its real Cellar path — which is why the
`site-checker` command and Finder work while Spotlight and Launchpad do not.
The README tells people exactly this, and it is correct.

## Findings

### F1 — Autostart LaunchAgent pins the Cellar path ([#25](https://github.com/clintcparker/site-checker/issues/25))

First launch enables "Launch at login" by default
([`src-tauri/src/lib.rs:45-62`](../../../src-tauri/src/lib.rs)) and
`tauri-plugin-autostart` writes:

```xml
<key>ProgramArguments</key>
<array><string>/opt/homebrew/Cellar/site-checker/1.0.0/libexec/Site Checker.app/Contents/MacOS/site-checker</string></array>
```

That is the **version-pinned Cellar path**. `brew upgrade` installs to
`Cellar/site-checker/1.0.1/` and removes `1.0.0/`, so the login item then points
at a path that no longer exists. The `/Applications` symlink was deliberately
pointed at `opt/` for exactly this reason; the LaunchAgent gets no such
treatment. `brew uninstall` also leaves the plist orphaned, and neither the
README's uninstall section nor the formula `caveats` mentions it.

Not blocking for `v1.0.0` — there is no upgrade to break yet. It breaks on the
**first** upgrade, so it wants fixing before `v1.0.1`.

### F2 — The tap is `Untrusted` under Homebrew's tap-trust regime

Homebrew 6.0.17 emitted a `Tap-Trust` warning during the install, and
`brew tap-info clintcparker/tap` reports `Untrusted`. The install **succeeded**
— trust is not enforced by default today. But Homebrew's own message says
the opt-out "will be removed in a later release", and the enforced behaviour is
that Homebrew *ignores* formulae from untrusted taps entirely, which would break
the documented one-liner until the user runs `brew trust clintcparker/tap`.

Worth a README line before Homebrew flips the default. Not observed at an
interactive TTY, so whether a real user currently sees a blocking prompt or only
the warning is unconfirmed.
