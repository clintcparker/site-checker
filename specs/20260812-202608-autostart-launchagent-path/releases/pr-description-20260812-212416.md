## Summary

Fixes [#25](https://github.com/clintcparker/site-checker/issues/25). Turning on "Launch at login" recorded the *exact copy* of the app that was running at the time — for a Homebrew install, a version-numbered path under `Cellar/site-checker/1.0.0/…` that the next upgrade deletes. macOS was left holding a login item pointing at nothing: Site Checker silently stopped opening at login while its own checkbox still said the feature was on. Nobody had hit it yet only because there had been no upgrade; it breaks on the first one.

This registers the version-independent path instead — `<prefix>/opt/site-checker/libexec/Site Checker.app/Contents/MacOS/site-checker`, the path Homebrew relinks on every upgrade — derived from the running executable's own location, so a relocated or non-default prefix needs no configuration. Registrations that are already stale repair themselves on the next start. Both uninstall surfaces now name the LaunchAgent.

**No user-visible UI change.** `src/`, `index.html`, `package.json` and `tauri.conf.json` are untouched, byte for byte; `pnpm test` reports the same 47 tests as `main`.

## Implementation

**New module — `src-tauri/src/autostart.rs`** (527 lines, 30 tests). Four pure decision functions plus a thin shell:

- `stable_path` — scans the running executable's path for a `Cellar` component and rewrites `…/Cellar/<formula>/<version>/<rest>` to `…/opt/<formula>/<rest>`. Requires three components after `Cellar` so a path ending at the version directory yields `None`.
- `desired_path` — accepts the derived path **only if** it exists *and* `canonicalize()`s back to the running executable. This is what makes the loose `Cellar`-component rule safe: a coincidental match (a user directory literally named `Cellar`) resolves to a different file or to nothing and falls back.
- `recorded_path` — a small string scan over the plist for `ProgramArguments[0]`. Deliberately strict: anything it did not write, it does not understand, and therefore leaves alone.
- `needs_repair` / `repair_with` — exact string comparison, with the write injected as a closure.

**Dependency swap.** `tauri-plugin-autostart` → `auto-launch` 0.5 directly. The plugin cannot be told which path to register, which is the entire fix; nothing else in the repo used it (`capabilities/default.json` never granted its JS commands, no companion npm package), so this is a net −30 lines of lockfile. `lib.rs` now owns the `AutoLaunch` as managed state and `commands.rs` reads it instead of using the plugin's extension trait.

**Wiring.** `repair_if_stale` runs inline in `setup`, after the first-run marker block, unconditionally — including for development builds.

Test count: **65 → 95** Rust (30 added). Frontend **47 → 47**, untouched.

### Judgment calls (agent-decided, unattended — please review)

1. **`tauri-plugin-autostart` removed rather than worked around.** Reversible in one commit if you prefer a vendored fork or an upstream PR; adding `set_app_path` upstream is worth doing separately either way.
2. **The plist is read with a string scan, not the `plist` crate.** The only files this must understand are ones the app wrote; a strict reader gives "leave everything else alone" for free with no new startup-path dependency. Accepted cost: a hand-written or binary registration is never repaired.
3. **Repair runs for development builds too.** Follows the spec's edge cases literally. A `#[cfg(debug_assertions)]` guard would spare developers having their real login item re-pointed at `target/debug`, at the cost of debug and release no longer being the same code path. Cheap to add.
4. **Path comparison is exact string equality**, not canonicalised. An equivalent-but-differently-spelled pre-existing path rewrites once and is then stable. Canonicalising both sides would hide a genuinely dead path behind a failed `canonicalize` and skip the repair that is the whole point.
5. **`repair_if_stale` is split around an injected write.** `tasks.md` T023 specifies `repair_if_stale(manager, plist_path)` calling `manager.enable()` directly, and that signature does ship — but `AutoLaunch::enable()` resolves its own target from `$HOME` and ignores the `plist_path` argument, so a test calling it would rewrite **the developer's real** `~/Library/LaunchAgents/Site Checker.plist` on every `cargo test`. The decision logic therefore lives in `repair_with(plist_path, desired, rewrite)`; tests drive that. If review prefers the literal signature, the cost is a test suite that mutates the developer's login item.

## Known issues

Everything here survives into `main` if this merges as-is.

### Open — from review

**W001 🟡 The template-drift guard the plan promises does not exist.** `plan.md`'s risk table, `tasks.md` T018, and the doc comment on `plist_template` all claim that "the reader tests assert against the exact template, so a change fails `cargo test` rather than silently disabling repair." They do not. `plist_template` is a `format!` string local to the test module; nothing in the suite ever calls into `auto_launch` to obtain a real template and compare. Every assertion proves the reader can read *the test's own string*. It is **already drifting** — `auto-launch` 0.5.0 ends its `format!` at `</plist>` with no trailing newline, the test's copy adds one. Harmless today, but proof the copy was hand-written and nothing keeps the two in step.

*Failure scenario*: someone bumps `auto-launch` to a version whose template differs. `cargo test`, `clippy` and CI all stay green, `recorded_path` returns `None` on every real file, `needs_repair` maps that to `false`, and repair silently stops working for every user — invisible until someone runs `brew upgrade` and loses launch-at-login again, i.e. **issue #25 reopened**. Exposure is a future bump, not this tree: `Cargo.lock` pins 0.5.0, but `Cargo.toml` requests `auto-launch = "0.5"`, a caret requirement that `cargo update` may move within.

*Recommended*: either make the claim true or retract it. Cheapest honest fix — retract the three comments and pin exactly (`auto-launch = "=0.5.0"`) so a template change requires a manifest edit a human reads. QA's harness does drive the real 0.5.0 `enable()` and parse its output (`H7`/`H7b`), so the check exists — just not as a `cargo test`-resident one.

**S001 🟢 "byte for byte" is not byte for byte.** `contracts/launch-agent-plist.md:27` claims the fenced block is exactly what `auto-launch` 0.5 writes; the real output has no trailing newline. Nothing depends on it, but a contract that says "byte for byte" invites someone to diff against it.

**S002 🟢 Two independent routes to the same `$HOME`.** `lib.rs:73-78` derives the plist path from Tauri's `home_dir()`; `AutoLaunch::enable()` derives its own from `dirs::home_dir()`. They agree today — but via *different crate versions in this lockfile* (`dirs` 4.0.0 for `auto-launch`, `dirs` 6.0.0 for Tauri), so the agreement is a coincidence of implementation. If they ever diverged, `repair_with` would read file A, decide "stale", rewrite file B — repairing nothing and rewriting on **every single start**. Worth one comment naming the coupling.

**S003 🟢 Harness config rides along.** See *Unrelated change* above.
