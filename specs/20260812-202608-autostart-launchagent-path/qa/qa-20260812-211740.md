## QA Summary

CLI QA, unattended, run against the worktree at
`/Users/clint/src/clintcparker/site-checker--20260812-202608-autostart-launchagent-path`
(feature resolved from `.specify/run-context.json`, confirmed by
`.specify/scripts/bash/check-prerequisites.sh`). No browser automation is configured in this project
and the app has no web surface, so every scenario was exercised through the three test suites plus a
purpose-built out-of-tree harness that links the **shipped** `autostart.rs` logic verbatim against the
**real** `auto-launch` 0.5.0 writer under a fake `$HOME` — 23 filesystem-level checks covering path
derivation, the plist round trip, all four repair decisions, and a simulated Homebrew upgrade. The
harness never touches the developer's real login item; that file and `sites.json` were SHA-verified
byte-identical before and after every pass.

Twenty of 21 scenarios passed on the first run. One failed: **TC-013 — the *registering* half of the
feature could abort startup**, which FR-008 forbids in those words. `autostart::manager()`
canonicalises `current_exe()`, which returns `ENOENT` when the running copy's own path has been
removed (demonstrated, not theorised — see the failure detail), and `lib.rs` propagated that with `?`
straight out of `setup` into `run().expect(...)`. This was fixed (managed state is now optional;
`setup` and both commands use `try_state` and degrade to a banner) and QA was re-run once. The second
run is green across all 21 scenarios and all three suites.

The verdict stays ⚠️ PARTIAL rather than ✅ because two scenarios remain structurally unrunnable
before this merges — a real `brew install` and a real `brew upgrade` need a released bottle
*containing this change* — and because the fix to TC-013 lives in the Tauri shell, which this project
has no harness to unit-test. Both are named below with the specific remaining gap.

**Screenshots**: `screenshots/` records `SKIPPED.md`, not `manifest.json`. The `before` pass judged
this feature to have no UI surface (`src/`, `index.html`, `assets`, `tauri.conf.json` all unmodified —
re-confirmed here by `git diff --stat origin/main -- src/ index.html package.json`, which is empty)
and so **never built or launched the app**. There is therefore no `capture_blocked: false` observation
to cite and no drivability evidence from that run; nothing in this report leans on one.

## Failure Details

### TC-013: A failure in the registering half stops the app starting

**Status**: ❌ FAIL on run 1 → ✅ fixed and re-verified on run 2
**Steps to Reproduce**:
1. Read `src-tauri/src/lib.rs:24` as it stood at `fe9db51`: `let autolaunch = autostart::manager(app.handle())?;`
2. `autostart::manager` is `std::env::current_exe()?.canonicalize()?` — both fallible.
3. Confirm `canonicalize()` really fails when the running copy's own path is gone: a throwaway binary that unlinks itself and then calls it returns `Err(Os { code: 2, kind: NotFound })` (`responses/current-exe-canonicalize.txt`). This is exactly what `brew upgrade` does to the keg an app was launched from.
4. Follow the `?`: it leaves the `setup` closure → Tauri's `run()` returns `Err` → `.expect("error while running tauri application")` panics. The window never opens.

**Expected**: FR-008 — "A failure at any point in registering or repairing MUST NOT prevent Site
Checker from starting"; SC-006 — no failure path introduced by this change can stop it starting.
**Actual**: The one non-swallowed error path in the feature aborted startup. The repair half was
correctly infallible; the registering half was not. (The staff review flagged the same line as W002.)
**Evidence**: `responses/current-exe-canonicalize.txt`; `git show fe9db51:src-tauri/src/lib.rs`
**Severity**: Medium — the requirement is unconditional and the trigger is an upgrade race, but the
window is the milliseconds between `exec` and `setup`, so it is narrow in practice.

**Fix applied** (this QA run, before the single permitted re-run):

- `lib.rs` — `manager()` is no longer `?`-propagated; the `AutoLaunch` is managed only if it could be built.
- `lib.rs` — the first-run marker block and the repair block both take it via `try_state`. An absent manager on first run raises the *same* user-facing warning a refused `enable()` does ("Could not turn on Launch at login (…)"), preserving the existing store-warning precedence. Repair is skipped entirely.
- `commands.rs` — a new `autolaunch()` helper returns `Err(String)` instead of panicking on an unmanaged `State`. The frontend already handles this: `mountAutostart` shows a banner and disables the checkbox (`src/main.ts:75-81`), so no frontend change was needed and none was made.

**Re-verification**: `cargo test` 95/95, `clippy -D warnings` clean, `pnpm test` 47/47, harness 23/23,
and greps confirming no `?` remains on the autostart path and no bare `.state::<auto_launch::AutoLaunch>()`
remains anywhere in `src-tauri/src/`.

**Residual gap**: the fix is in the Tauri shell, which this project has no harness to unit-test
(Principle IV puts the tested logic in `autostart.rs`, and that file is unchanged). It is verified by
compilation, by the static greps above, and by reading — not by a test. Adding a Tauri integration
harness is out of scope for this feature.

### TC-006 / TC-021: the real Homebrew upgrade (⚠️ partial, 🔵 skipped)

**Status**: ⚠️ partial (TC-006) / 🔵 skipped (TC-021) — not a defect
**Why**: Both need a released bottle *containing this change*, which does not exist until this merges.
The spec says so itself ("Verification of the upgrade path requires two real builds … no automated
test can observe a package-manager upgrade").
**What was done instead**: the harness builds a real keg at
`<prefix>/Cellar/site-checker/1.0.0/libexec/Site Checker.app/Contents/MacOS/site-checker`, links
`<prefix>/opt/site-checker` at it, registers through the real `AutoLaunch::enable()`, then performs
the upgrade — creates `1.0.1`, repoints the `opt` symlink, **deletes the `1.0.0` keg** — and re-reads
the plist. The recorded path still exists and canonicalises to the 1.0.1 executable (`H2`), while the
path the pre-fix code would have recorded is now missing (`H2b`).
**Remaining gap, precisely**: what is *not* covered is Homebrew itself — bottle relocation, the
`bin` wrapper, code signing, and macOS actually honouring the LaunchAgent at a real login. The
path-resolution mechanism SC-001 depends on is covered.

## Other findings recorded during QA

- **`quickstart.md` §2d was wrong and has been corrected.** The harness proved it: with only the
  *directory* made read-only (`chmod 500 ~/Library/LaunchAgents`, as §2d said), the rewrite still
  **succeeded** — truncating an existing file needs write permission on the file, not its parent — so
  the step proved nothing (`H13b`). §2d now says `chmod 400` on the plist itself, which is what makes
  `File::create` fail, and which `H13` confirms is swallowed. This matches what
  `implementation-notes.md` already said should be amended.
- **The contract-drift gap the staff review raised as W001 is now covered by evidence**, though not by
  a test in the repo: `H7`/`H7b` drive the real `auto-launch` 0.5.0 `enable()` and parse its output
  with the shipped `recorded_path()`, including a path containing a space. If upstream changes its
  template, this harness fails. A `cargo test`-resident version of that check is still absent.
