## Executive Summary

**The defect in issue #25 is fixed, the fix is correct, and it is the narrow fix the spec asked
for.** All twelve functional requirements are implemented; all three quality gates are green on
this branch (95 Rust tests, 47 frontend tests, `clippy -D warnings` clean); the frontend is
untouched, byte for byte, exactly as the spec's "no user-visible UI change" assumption requires.

The core derivation was verified against reality rather than taken on trust. `auto-launch` 0.5.0's
macOS `enable()` writes `ProgramArguments[0]` from `self.app_path` verbatim, and the formula
installs the bundle at `#{opt_libexec}/Site Checker.app` — so the path this module derives
(`<prefix>/opt/site-checker/libexec/Site Checker.app/Contents/MacOS/site-checker`) is precisely the
path Homebrew relinks on every upgrade. The `desired_path` guard — accept the derived path only if
it exists *and* `canonicalize()`s back to the running executable — is the right shape: it makes
`stable_path`'s loose "find a `Cellar` component" rule safe to state loosely, because a coincidental
match resolves to a different file or to nothing and falls back.

The module/shell split the constitution's Principle IV asks for is honoured better here than in most
of this repo: four decisions are pure functions with 30 tests, the Tauri-dependent part is eleven
lines in `lib.rs` and two one-line command bodies, and `repair_with` exists as a seam precisely
because `AutoLaunch::enable()` resolves its own target from `$HOME` and a test that called it would
rewrite the developer's real login item. That seam is not over-engineering; it is the only way this
is testable at all.

**Three conditions, none of them blocking.** One is a mitigation the plan promises and the code does
not deliver (upstream template drift is *not* detected by any test, despite `plan.md` and `T018`
both saying it is). One is a literal FR-008 deviation on the single error path in the feature that is
not swallowed — `manager(...)?` can still abort startup. One is a verification step this branch
itself documented as wrong and then shipped unamended, which will hand the next person a false pass.

**What could not be verified here, and is honestly recorded as such**: quickstart §3 and §4 — a real
`brew install` and a real `brew upgrade` — need a released bottle containing this change, which does
not exist until this merges. `implementation-notes.md` says so, `T034` requires the PR to say so, and
this review confirms the gap is real rather than an omission. Until that first release, `Cellar → opt`
is covered by path-string unit tests plus one `tempfile` test that builds a real `opt/<formula>`
symlink to a real keg directory — which is as close as a checkout can get.

### W001 — 🟡 The template-drift test does not test template drift

**Where**: `src-tauri/src/autostart.rs:320–340` (`plist_template`), with the claim repeated at
`autostart.rs:320–323`, `plan.md:189` (Risks, last row) and `tasks.md:117` (T018).

**The claim.** `plan.md`'s risk table says: *"`auto-launch` changes its template in a future version →
The version is pinned in `Cargo.lock` and the reader tests assert against the exact template, so a
change fails `cargo test` rather than silently disabling repair."* T018 repeats it. The doc comment
on `plist_template` repeats it a third time: *"Asserted against verbatim so that a future
`auto-launch` template change fails this test rather than silently disabling repair."*

**What the code does.** `plist_template` is a `format!` string local to the test module. Nothing in
the suite ever calls into `auto_launch` to obtain a real template and compare. Every assertion is
`recorded_path(plist_template(x)) == Some(x)` — the test proves the reader can read the *test's own*
string. If `auto-launch` 0.6 reformats the plist, all 30 tests stay green and `recorded_path`
returns `None` on every real file, which `needs_repair` maps to `false`, which means repair silently
stops working for every user — the precise failure the claim says is prevented.

**Evidence it is already drifting.** `auto-launch` 0.5.0 `src/macos.rs` builds its `format!` ending
in `</plist>` with no trailing newline. The test's copy ends `</plist>\n`. Harmless to
`recorded_path`, but it is proof the copy was written by hand rather than derived, so nothing keeps
the two in step.

**Exposure.** `Cargo.toml` requests `auto-launch = "0.5"`, a caret requirement: `cargo update` may
move to any `0.5.x` without a manifest edit. `Cargo.lock` pins `0.5.0` today, so the risk is a
future bump, not the current tree — which is why this is a Warning and not a Blocker.

**Failure scenario**: maintainer bumps `auto-launch` to a version whose template differs (say, an
`<array>` split across lines, or two-space indent changed to a tab). `cargo test` green, `clippy`
green, CI green, PR merges. Every user's stale registration stops being repaired, and every user
whose registration is already correct is unaffected — so the regression is invisible until someone
upgrades Homebrew and loses launch-at-login again, which is issue #25 reopened.

**Recommendation**: either make the claim true or retract it. Cheapest honest fix is to retract —
change the three comments to say the reader is deliberately tolerant of *this* template only, and
pin the dependency exactly (`auto-launch = "=0.5.0"`) so a template change requires a deliberate
manifest edit that a human reads. A stronger fix, if the seam is wanted: have `repair_with` take the
already-read contents, add a test that constructs a real `AutoLaunch` pointed at a `tempfile` binary,
calls `enable()` with `$HOME` overridden to a temp dir, and asserts `recorded_path` reads back what
it wrote. (`dirs::home_dir()` reads `$HOME` on macOS, so a scoped env override is enough — but it is
process-global, so that test must be serialized.)

### W002 — 🟡 The one error path that is not swallowed can stop startup

**Where**: `src-tauri/src/lib.rs:24` — `let autolaunch = autostart::manager(app.handle())?;`

**Against**: FR-008 — *"A failure at any point in registering or repairing MUST NOT prevent Site
Checker from starting"* — and SC-006, which asserts the same for every failure path this change
introduces.

`manager()` is `std::env::current_exe()?.canonicalize()?`. Both `?`s escape `manager`, and the `?`
at the call site escapes the `setup` closure, which is how a Tauri app fails to launch. Every other
step in this feature is deliberately infallible: `repair_if_stale` swallows its read error, swallows
`enable()`'s error, and is itself guarded by `if let Ok(home)`. The registering half is the
exception, and it is the half FR-008 names first.

**Failure scenario**: `current_exe().canonicalize()` fails with `ENOENT` because the executable's
path stopped resolving between `exec` and `setup` — the realistic window is a `brew upgrade`
deleting the old keg while the app is launching out of it, which is the very event this feature is
about. Result today: the app does not open, with no window and no message. Expected per FR-008: the
app opens; only the registration is skipped.

**Mitigating, and why this is not a Blocker**: this is not a regression.
`tauri-plugin-autostart` 2.5.1 did exactly the same thing — its plugin `setup` ran
`current_exe()?` and `current_exe.canonicalize()?` and propagated both. The branch preserves
pre-existing behaviour rather than introducing a new failure. It also sits alongside
`app.path().app_config_dir()?` a few lines below, which has always been able to abort startup the
same way. So the exposure is unchanged from `main`; what changed is that a spec now says it must not
happen.

**Recommendation**: fall back rather than propagate — `current_exe()` un-canonicalized if
`canonicalize()` fails, and a last-resort empty-path `AutoLaunch` if `current_exe()` itself fails.
Note that skipping `app.manage(...)` is *not* an option: `app.state::<AutoLaunch>()` in
`commands.rs:139,148` panics when nothing is managed, which would turn a silent no-launch into a
panic the first time the user touches the checkbox. Something must always be managed. An
`AutoLaunch` built from a path that does not exist is harmless — `enable()` returns
`AppPathDoesntExist`, which both call sites already handle.

### W003 — 🟡 A verification step known to be wrong shipped unamended

**Where**: `specs/.../quickstart.md:111–116` (§2d), contradicted by
`specs/.../implementation-notes.md:80–84`.

The quickstart says: *"Repeat 2b and 2c with `~/Library/LaunchAgents` made unwritable (`chmod 500`),
so the rewrite itself fails."* The implementation notes say, correctly, that this proves nothing —
`enable()` calls `File::create` on an **existing** file, which needs write permission on the *file*,
not on the directory, so the rewrite succeeds and §2d passes without testing anything. The notes
record that the step was re-run with `chmod 400` on the plist, that only then does it fail with
`EACCES`, and state outright: **"quickstart.md §2d should be amended."** It was not amended.

**Failure scenario**: the next person to run the documented FR-008/SC-006 gate — a release check, a
reviewer, a future `/speckit-qa-run` — follows §2d as written, sees the app start, and records
SC-006 as verified. The rewrite never failed, so nothing about the failure path was exercised. A
false pass on the one criterion that says no new failure path can stop the app starting.

**Recommendation**: one-line edit to §2d — `chmod 400 ~/Library/LaunchAgents/"Site Checker.plist"`
(and restore with `chmod 600`), keeping the directory `chmod 500` step only for the create-path
case. The evidence and the corrected procedure are already written in `implementation-notes.md:80–84`;
this is transcription, not new work.

### S001 — 🟢 "byte for byte" is not byte for byte

`contracts/launch-agent-plist.md:27` — *"Exactly what `auto-launch` 0.5 writes, byte for byte."* The
real `format!` in `auto-launch-0.5.0/src/macos.rs` terminates at `</plist>` with no trailing
newline; the contract's fenced block (and the test's `plist_template`) both end with one. Nothing
depends on it — `recorded_path` never looks past `</array>` — but a contract that says "byte for
byte" invites someone to diff against it. Either drop the trailing newline or soften the claim to
"structurally what `auto-launch` 0.5 writes; only `ProgramArguments[0]` is read."

### S002 — 🟢 Two independent routes to the same `$HOME`

`lib.rs:73–78` computes the plist path from `app.path().home_dir()`; `AutoLaunch::enable()` computes
its own from `dirs::home_dir()`. Verified they agree: `tauri-2.11.5/src/path/desktop.rs:153` *is*
`dirs::home_dir()`, and on macOS both resolve `$HOME`. But the two arrive via different crate
versions in this very lockfile (`dirs` 4.0.0 for `auto-launch`, `dirs` 6.0.0 for Tauri), so the
agreement is a coincidence of implementation, not a guarantee. If they ever diverged, `repair_with`
would read file A, decide "stale", and rewrite file B — repairing nothing and rewriting on every
single start. Worth one comment at `lib.rs:73` naming the coupling, so a future reader knows the two
paths must stay identical.

## Review Pass Notes

### Pass 1 — Correctness & logic

`stable_path` was checked component by component against `Path::components()`, which yields
`RootDir` as element 0. For `/opt/homebrew/Cellar/site-checker/1.0.0/libexec/…`, `cellar = 3` and
`i + 3 < len` requires a non-empty remainder after the version — correct, and correctly rejects both
truncated shapes the tests name. `out.extend(&parts[..cellar])` starts by pushing `RootDir`, which
`PathBuf::push` handles as an absolute reset; since it is the first push, the result is right. The
deepest-match search (`.rev().find_map`) is the right choice and the reason is stated in the code.

The end-to-end path was traced for each install shape in the contract's table, including the one the
spec calls out as an edge case: launching through the optional `/Applications` symlink. The formula's
`bin` wrapper is `open -a "#{opt_libexec}/Site Checker.app"`, so the process starts from the `opt`
path; `canonicalize()` in `manager()` collapses it to the keg; `stable_path` derives the `opt` path
back; `desired_path`'s `canonicalize()` check confirms it resolves to the same executable. Both
launch routes converge on one recorded path, as the contract claims.

Error handling in the repair half is genuinely infallible by construction: `read_to_string(...).ok()`
turns both "missing" and "unreadable" into `None`, `needs_repair(None, _)` is `false`, and the
`enable()` result is discarded. The absent-file and unreadable-file cases collapsing into one branch
is deliberate and documented (FR-006 + FR-007 both mean "do nothing"), and it is the right call —
distinguishing them would only create a code path with nothing to do in it.

`recorded_path`'s bounds are correct and non-obvious, and both are tested: starting the scan *after*
`<key>ProgramArguments</key>` prevents the `Label` string (which appears earlier in the real
template) from being read as the program, and clipping at `</array>` prevents a later key's
`<string>` from being read as one when the array is empty.

No race conditions: everything runs inline on the setup thread before `AppState` is managed and
before any command can be invoked. No concurrent access to the plist is possible from within the
app.

### Pass 2 — Security

Nothing security-sensitive is introduced. No network, no shell, no user input reaches any of this
code. The one write is to a fixed path under the user's own `$HOME` and it is a truncating rewrite of
a file this app authored. Path traversal is not reachable: the recorded path is derived from
`current_exe()`, not from anything a user or a file supplies — note in particular that the *read*
path (`recorded_path`) is only ever compared, never opened, executed, or written back out, so a
hostile plist cannot steer the app anywhere. The `Cellar → opt` rewrite is string surgery on an
already-canonicalized path. No secrets, no logging, no error surfaced to the UI (deliberately, per
FR-007).

One thing worth stating plainly because it looks like a risk and is not: this feature writes a path
into a file that macOS will later execute at login. If an attacker could make `desired_path` return
a path they control, that would be a persistence primitive. They cannot — the derived path is
rejected unless it `canonicalize()`s to the currently running executable, which means the only
program that can ever be recorded is the one already running.

### Pass 3 — Performance

One `read_to_string` of a ~400-byte file on startup, plus at most one `canonicalize()` and, only when
stale, one small write. `plan.md` measured this in microseconds and the reasoning for keeping it
inline rather than deferring it (it would race `set_autostart`) is sound. No leaks: no handles are
held, no listeners registered, `AutoLaunch` is four `String`s in managed state.

Every FR maps to code; see the coverage matrix below. The architecture in `plan.md` §Design was

### Pass 5 — Test quality

30 new tests, and they are the right 30 — each maps to a row of quickstart §1, and the negatives
outnumber the positives, which is correct for a feature whose main job is knowing when *not* to act.
Assertions are meaningful (exact `PathBuf` equality, exact extracted strings), not "doesn't throw".
Isolation is clean: every filesystem test builds its own `tempfile::tempdir()`, and none touch
process-global state — notably, none set `$HOME`, which is what makes them safe to run in parallel
alongside a developer's real login item.

Two details worth calling out as good:

- `a_derived_path_that_resolves_back_to_the_running_copy_is_recorded` builds a real `opt/<formula>`
  symlink to a real keg directory, and canonicalizes `dir.path()` first because `/var → /private/var`
  on macOS would otherwise make the assertion compare two spellings of the same path. That is a bug
  the test would have hit, anticipated and handled.
- `repaired()` asserts `plist.exists() == plist_contents.is_some()` on every call, which proves the
  module never creates or deletes the file itself — the FR-006/FR-012 guarantee — rather than merely
  proving the closure did not fire.

The gaps, in order of significance:

1. **Upstream template drift is untested and claimed to be tested** — W001 above.
2. **The `lib.rs` wiring is untested**, so the ordering guarantee that makes the whole design work
   (first-run `enable()` *before* `repair_if_stale`, so a genuine first run finds nothing to repair)
   is asserted only in prose. Accepted: Principle IV explicitly permits a shell thin enough not to
   need tests, and this one is. Recorded so it is a known choice, not an oversight.
3. **`manager()` itself is untested** — it is the only function that reads `current_exe()`, and it
   is where W002 lives.
