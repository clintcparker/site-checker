## Implementation

### US1 — Remove the dead opener plugin (P1) 🎯 MVP

The roadmap named two declarations; inspection found a third. `src-tauri/src/lib.rs` only
ever initialized `tauri_plugin_autostart`, so the plugin was being granted permission
surface *and* compiled into the shipped binary without ever being used. All three
declarations were removed together — leaving the Rust crate behind would have kept
compiling it in:

- `"opener:default"` → out of `src-tauri/capabilities/default.json` (leaving `"core:default"`)
- `@tauri-apps/plugin-opener` → out of `package.json`
- `tauri-plugin-opener` → out of `src-tauri/Cargo.toml`

Both lockfiles regenerated and committed, so a clean checkout does not reinstall a
dependency the manifest no longer declares (`src-tauri/Cargo.lock` shed 404 lines).

### US2 — Delete orphaned scaffold assets (P2)

`src/assets/tauri.svg`, `typescript.svg`, and `vite.svg` deleted. No source file or
`index.html` referenced them, and Vite already excluded them from the bundle, so `dist/`
is unchanged against the pre-change reference listing. `src/assets/` was empty afterward
and was removed too.

### US3 — Fix scaffold identity metadata (P2)

The one story that could break the build. `src-tauri/Cargo.toml` set
`[lib] name = "tauri_app_lib"` and `src-tauri/src/main.rs` called `tauri_app_lib::run()`;
renaming either alone fails to compile, so they landed as a single atomic change.

- `package.json`: `"name": "tauri-app"` → `"site-checker"`
- `src-tauri/Cargo.toml`: `name = "site-checker"`, a real one-line `description`,
  `authors = ["Clint Parker <me@clintparker.com>"]` (was `["you"]`)
- `[lib] name`: `tauri_app_lib` → `site_checker_lib`, with `main.rs` updated in the same edit

`src-tauri/tauri.conf.json` never referenced the crate name, so the bundle is unaffected:
`pnpm tauri build --bundles app` still emits `Site Checker.app` with identifier
`com.clintparker.site-checker`.

### US4 — Make two strings say what they mean (P3)

- `src-tauri/src/store.rs::load` — the parse-error arm now reads
  `"sites.json is not valid JSON ({e}). Starting with an empty list; ..."` instead of
  `"sites.json could not be read ({e}). ..."`, which was indistinguishable from the
  neighbouring I/O-error arm (`"Could not read sites.json ({e}). Starting empty."`).
  The two no longer share an opening phrase. **This is the only user-visible change in the PR.**
- `src-tauri/src/model.rs` — the `has_leading_scheme` doc comment now states the rule its
  body actually applies: the text before `://` must be entirely ASCII alphanumeric or one
  of `+`, `-`, `.`.

### Sequencing

US1 and US3 both edit `package.json` and `src-tauri/Cargo.toml` — the only cross-story file
conflict in the feature — so they were serialized. US2 and US4 touch disjoint files. Each
story is a standalone commit and a standalone revert, and each ended with its own gate run.

> `specs/001-scaffold-cleanup/screenshots/` contains a manifest and **no images**. This is an
> environment permissions problem, **not an implementation defect**: the agent's host process
> (a VS Code tunnel/remote server) has no GUI attribution, so it can hold neither the macOS
> **Screen Recording** grant that `screencapture` needs nor the **Automation → System Events**
> grant that window positioning needs. Permissions attach to the responsible process, so
> nothing spawned from it inherits them.
>

> rather than assumed:
> - `screencapture -x` → `could not create image from display` (exit 1), no file produced

>   window being absent is not the cause.

> This is **not** a headless environment; a GUI session exists, the agent simply cannot reach it.
> Fixing it needs a human at the machine to grant Screen Recording and Automation to the host
> app in System Settings → Privacy & Security. Both prompts are interactive.
