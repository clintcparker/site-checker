## Executive Summary

This is unusually disciplined work, and the design choices are the reason rather than the test
count. All three fixes are structural rather than call-site edits: `SharedStore` has no accessor
for its inner mutex, so an unrecovered lock on the site list is *unwritable* outside `lock.rs`;
`Store::replace` collapses the read-decide-write into one `&mut self` borrow, so FR-013 holds

## Review Passes

### Pass 1 — Correctness & Logic

- **`recover`'s poison semantics are right.** `mutex.clear_poison()` does not itself acquire the
  lock, so calling it while `poisoned` still holds the guard is not a self-deadlock, and it makes
  L5 literally true: a second thread blocked in `lock()` observes the cleared flag only after the
  first thread's guard drops, so two threads cannot both report one fault. Pinned by
  `a_second_recovery_reports_clean_so_no_degraded_mode_accumulates`.
- **Guard lifetimes are correct at every call site**, and were checked individually rather than
  assumed. `commands.rs:69` binds `stored` so the temporary drops at the semicolon, before the
  match; `commands.rs:108–116` uses an explicit block so the guard drops before `reschedule`;
  `engine.rs:78` binds `removed` so the guard drops before `abort`; `engine.rs:125`'s guard is
  function-local and never crosses an `.await`, so `run_site` stays `Send`.
- **Every shared-state access recovers.** All eight `.lock(` occurrences in the crate were
  enumerated: `lib.rs:37`, `commands.rs:25/69/109/131`, `engine.rs:125` go through
  `SharedStore::lock`; `lock.rs:28` is `recover` itself; `lock.rs:236` is the guard test's needle.
  The three flag-discarding sites (`engine.rs:62`, `engine.rs:78`, `commands.rs:33`) each carry the
  justifying comment the contract demands. No `.lock().unwrap()` remains.
- **One behaviour is strictly better than before, in the spec's own direction.** Under the old
  two-lock `update_site`, a site deleted between the `get` and the `update` produced a no-op-save
  and an `Ok(site)` with a resurrected timer. `Store::replace` returns `None` with no save, so the
  user is told the site no longer exists — which is what the spec's "A site is deleted between an
  edit being started and applied" edge case and FR-014 actually require.
- **Half-applied state survives recovery** (FR-006) and is pinned directly by
  `recovery_preserves_what_the_faulting_operation_had_already_applied`, not merely asserted.

### Pass 3 — Performance & Scalability

No regression, and none plausible. `recover` on a healthy mutex is one `match` over the same
`Mutex::lock` call — L2/L6 hold by construction. `clear_poison` runs only on the recovery path,
which in a healthy session never runs. Lock hold times are unchanged except that `update_site` now
holds **one** guard where it previously took two (the 10 → 9 collapse). No allocation, no
`.await` under a guard, no unbounded growth. R003's emit-under-guard is the only hold-time change
and only on the fault path.
