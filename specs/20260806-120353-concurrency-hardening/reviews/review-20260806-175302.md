## Review Passes

### Pass 1 — Correctness & Logic

- **`recover`'s poison semantics are right, and the ordering is deliberate.** `clear_poison()` is
  called before `into_inner()`, while the guard inside the `PoisonError` is already held.
  `clear_poison` does not itself acquire the lock, so this is not a self-deadlock. It makes the
  report genuinely one-shot: a second thread blocked in `lock()` observes the cleared flag only
  after the first thread's guard drops, so two threads cannot both report one fault. Pinned by
  `a_second_recovery_reports_clean_so_no_degraded_mode_accumulates`.
- **Guard lifetimes are correct at every call site**, checked individually. `commands.rs:69` binds
  `stored` so the temporary drops at the semicolon rather than surviving to the end of the `match`;
  `commands.rs:108–116` uses an explicit block so the guard drops before `reschedule`;
  `engine.rs:78` binds `removed` so the guard drops before `abort` — a real improvement over the old
  `if let Some(h) = self.inner.tasks.lock().unwrap().remove(id)`, which held the guard for the whole
  `if let` body; `engine.rs:125`'s guard is function-local and never crosses an `.await`, so
  `run_site` stays `Send`.
- **No lock-order inversion exists.** `Engine::start` holds the `tasks` guard across
  `async_runtime::spawn`, but never takes the store lock; `persist_get_fallback` takes the store lock
  and never touches `tasks`; `add_site`/`update_site`/`delete_site` release the store lock before
  calling into the engine. The order is one-way, so R003's emit-under-guard cannot become a deadlock.
- **One behaviour is strictly better than before, in the spec's own direction.** Confirmed against
  the diff rather than inferred: the old `update_site` did `get` → build → `update`, and `update` on
  a missing id was a no-op-then-save returning `Ok` — so a site deleted between the two locks
  produced `Ok(site)`, a resurrected row, *and* a restarted timer. `Store::replace` returns `None`
  with no save, so the user is told the site no longer exists. That is what FR-014 #4 and the
  "deleted between an edit being started and applied" edge case require.
- **Half-applied state survives recovery** (FR-006), pinned directly by
  `recovery_preserves_what_the_faulting_operation_had_already_applied` rather than merely asserted.
- **SC-001 holds structurally.** A panic in any command, in a spawned check task, or in
  `Engine::start` poisons exactly one of the three mutexes, and every access to all three recovers.
  No path leaves the app unable to accept input.

### Pass 3 — Performance & Scalability

No regression, and none plausible. `recover` on a healthy mutex is one `match` over the same
`Mutex::lock` call. `clear_poison` runs only on the recovery path, which a healthy session never
enters. Lock hold times are unchanged except that `update_site` now holds **one** guard where it
took two. One small note, below the bar for a finding: `empty_to_none` and `clamp_interval` are now
evaluated inside `update_site`'s lock scope as arguments to `replace`, where they used to run before
any lock — a string trim and a clamp, immaterial next to the `save()` that already happens under
that guard. No allocation growth, no `.await` under a guard, no unbounded collection.

### Pass 5 — Test Quality

The Rust suite went 42 → 55 and the additions are meaningful rather than volumetric.

- The **negative control** (`the_old_two_lock_shape_would_lose_the_earlier_edit`) drives the identical
  choreography through the old shape and asserts the bug. Both tests share one `run_overlapping_edits`
  function, so they cannot drift apart — this is what makes the positive test non-vacuous permanently.
- **I traced the barrier choreography for deadlock and flakiness rather than trusting it.**
  `Barrier::new(2)` with exactly two `wait()` calls per thread across two generations; no lock is
  held across either barrier in either helper. In the two-lock case the earlier edit provably
  completes strictly inside the later edit's read→write window, so the stale read is deterministic,
  not merely likely. In the atomic case the window can only sit *before* the lock — the helper says
  so, which is the honest framing: `edit_atomically` proves `replace` decides from current state, not
  that it survives a true overlap, because `replace` has no overlap to survive.
- Poison injection is deterministic (spawn → panic under guard → join, discarding `Err`), with two
  assertions that the helper actually poisoned something so the tests cannot pass vacuously. The
  planned `set_hook` dance was dropped for a stated, measured reason.
- Assertions are specific: `matches!(…, Err(AddError::DuplicateId(_)))` rather than `.is_err()`, and
  the refusal test asserts on the **reloaded file** plus the absence of a staging artifact, which is
  what proves the refusal preceded any write.
- Gaps, all declared in advance: the `store-warning` emit wiring and `add_site`'s refusal ordering are
  verified by eye (R002), and the guard test's coverage is narrower than its stated purpose (R001).
