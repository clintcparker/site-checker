## QA Summary

Thirty-one scenarios were derived from the spec's thirteen acceptance scenarios, eighteen
functional requirements, and eight success criteria, and run in CLI QA mode against the merged
implementation in the primary checkout (`src-tauri/src/{lock,store,commands,engine,lib}.rs`).
Site Checker is a Tauri desktop app whose command layer is reachable only through a native window,
and `package.json` carries no Playwright/Puppeteer/Cypress/Selenium dependency — so no *browser*
driver applies. That is not the same as the window being undrivable: the screenshot extension's
capture passes drive it directly through the macOS accessibility API, and the two window-dependent
scenarios are covered by those runs. Twenty-nine scenarios passed, none failed, two are partial, and
none were skipped.

Every behaviour the feature exists to fix is proven by a test that actually runs. Fault recovery is
exercised against a genuinely poisoned mutex; the refused-add distinction is asserted on the
`AddError` variant and on the reloaded file's bytes; the overlapping-edit fix is proven against a
negative control that drives the *identical* barrier choreography through the old two-lock shape and
asserts the bug is present. All three merge gates are green from a clean run of this checkout —
Rust 55/0/0, frontend 30/0 unmodified, clippy clean at both `-D warnings` and `--all-targets`.
`grep -rn 'lock()\.unwrap()' src-tauri/src/` returns nothing, and all nine remaining lock sites were
enumerated: six route through `SharedStore::lock`, three through `lock::recover(..).0` each carrying
the reason the flag is discarded.

Both partials trace to the same pre-declared gap, the open condition R002 from
[review-20260806-144450.md](../reviews/review-20260806-144450.md): the shell layer (`commands.rs`)
has no automated coverage by design (Constitution IV, research R7), and the manual click-through
that was supposed to stand in for it — add, edit, and delete against a running window — was only
partly performed. The screenshot passes did drive the window: five launches, the list loading with
resolved statuses, and an add submitted through `#site-url` and correctly refused. What they did not
do is complete a *successful* add, or perform any edit or delete. To narrow the remainder with
machine evidence rather than leave it bare, this run added a wire-contract cross-check that parses
the seven `#[tauri::command]` signatures out of `commands.rs` and matches them argument-for-argument
against the `invoke()` calls in `src/api.ts`. It passes for all seven, including the two commands
(`update_site`, `delete_site`) that changed signature in this feature and were the specific risk R002
named. What remains unverified is narrower than R002 described, but it is not zero: `update_site` and
`delete_site` have still been exercised by neither machine nor hand.

### TC-005: A recovered site-list lock raises exactly one banner

**Status**: ⚠️ PARTIAL
**Steps to Reproduce**:
1. Poison the site-list mutex from a thread that panics under the guard.
2. Take the next `SharedStore::lock()`.
3. Observe whether one `store-warning` event is emitted with the FR-004 message.

**Expected**: exactly one banner, on the existing `store-warning` channel, saying the saved list may
not reflect the most recent change.
**Actual**: steps 1 and 2 are proven at runtime (`recover_returns_a_usable_guard_after_a_fault_and_reports_it`,
`a_second_recovery_reports_clean_so_no_degraded_mode_accumulates`). Step 3 was verified by reading
`lock.rs:76–85`: the `recovered` flag gates a single `self.warn(...)` whose message matches FR-004,
and `warn` is the crate's only `emit` of `store-warning`. There is no runtime assertion on the emit
because it needs an `AppHandle`; the `tauri` `test` feature and a mock-app harness were declined at
research time (R7) rather than added for three lines of `emit`.
**Evidence**: `src-tauri/src/lock.rs:76–108`; [us1-lock.txt](responses/us1-lock.txt)
**Severity**: Low — declared in advance in `plan.md` and `tasks.md`, not discovered here. The event
name and `{ message }` payload are unchanged, so `src/main.ts:109`'s `onStoreWarning(showBanner)`
needs nothing new.

### TC-030: GUI click-through — add, edit, delete against a running window

**Status**: ⚠️ PARTIAL *(corrected from 🔵 SKIPPED — see the correction note at the top)*
**Steps to Reproduce**:
1. `pnpm tauri dev`.
2. Add a site, edit it, delete it.
3. Confirm each behaves exactly as before the feature (FR-007).

**Expected**: all three unchanged from pre-feature behaviour.
**Actual**: **add exercised, edit and delete not.** The screenshot passes drove the running window

(`14ea8e47ee96bce426d659a7249d764824dc9744` both times). So the *refused* add path is confirmed
end-to-end through the UI. No **successful** add, no edit, and no delete was performed. This is open
condition R002 from the staff review, narrowed to those two commands; tasks T025 and T040 remain
partially done for the same reason.
**Evidence**: [manifest.json](../screenshots/manifest.json) — `views[add-error]`,
`environment.after_run`, and the closing note ("the delete and edit click-throughs were still not
exercised"). [wire-contract.txt](responses/wire-contract.txt) narrows the remainder further — all
seven command signatures match `src/api.ts` argument-for-argument, including `update_site` and
`delete_site`, the specific risk R002 named.
**Severity**: Medium — it is the FR-007 "nothing else changed" check, not a check of any new
behaviour, and every store-layer path underneath it is covered by a passing test. The remaining
edit/delete click-through should be run by hand before merge or recorded in the ship notes as an
accepted residual.
