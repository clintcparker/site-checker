## QA Summary

Thirty-two scenarios were derived from the spec's thirteen acceptance scenarios, eighteen functional
requirements and eight success criteria, and run against the merged implementation in the primary
checkout (`src-tauri/src/{lock,store,commands,engine,lib}.rs`, HEAD `3e9972c`). **Thirty-one passed,
none failed, one is partial, none were skipped.** All three merge gates are green from a clean run of
this checkout: Rust 55/0/0, frontend 30/0 unmodified, clippy clean at both `-D warnings` and
`--all-targets -- -D warnings`.

This run is not a re-derivation of [qa-20260806-145201.md](./qa-20260806-145201.md). It closes that
report's open item. The prior run left two partials, both tracing to review finding R002 — the shell
layer (`commands.rs`) has no automated coverage by design (Constitution IV, research R7), and the
manual click-through meant to stand in for it had only ever been partly performed: a *refused* add
through the UI, but **no successful add, no edit, and no delete against a running window**. This run
performed all three. The app was launched three times, driven with real synthetic mouse clicks
through the macOS accessibility API, and the user's saved list was hashed and parsed at every step:

- **Add** — a site typed into the form and submitted. `sites.json` went 3 → 4 entries with a freshly
  minted UUID, the row appeared, its check started (Pending → Down), no banner.
- **Edit** — that row's Edit button clicked, the form populated from the site, label and interval
  changed, Save clicked. Same id, same URL, both fields updated, **still at index 3** — list order
  preserved through a replace.
- **Delete** — that row's Delete button clicked. `sites.json` back to 3 entries, the other three
  untouched and in order; the row did not return after a relaunch.

A sixth interaction went beyond the open item. With the app running, the store's directory was made
unwritable and a valid non-duplicate site was added. The `#banner` element rendered *"Could not write
sites.json: Permission denied (os error 13)"*, the row appeared anyway, its check ran to Down, and
`sites.json` on disk stayed byte-identical. That is FR-011 and US2-AS3 proven at runtime for the first
time — and, because `lock.rs:103` is the crate's only emit of `store-warning` and `SharedStore::lock`'s
FR-004 warning goes through the same private `warn()` helper, it is also the first runtime proof of the
**mechanism** FR-004 reuses.

**The one remaining partial is TC-005**, and it is now strictly narrower than it was. What is still
unproven at runtime is only the poison-specific *trigger*: that a recovered mutex sets the flag that
calls `warn()` with FR-004's wording. Both halves either side of it are proven — recovery by the lock
tests, the emit-to-banner path by TC-032 above — and the gate and the string itself are verified by
reading `lock.rs:76–85`. No sequence of clicks can poison a mutex, so this cannot be closed by driving
the window; closing it needs the `tauri` `test` feature and a mock-app harness, declined in advance at
research time (R7). The FR-010 duplicate-id refusal is unreachable by clicking for the same kind of
reason — every add mints a fresh id — and stays covered by the automated tests.

### TC-005: A recovered site-list lock raises exactly one banner

**Status**: ⚠️ PARTIAL
**Steps to Reproduce**:
1. Poison the site-list mutex from a thread that panics under the guard.
2. Take the next `SharedStore::lock()`.
3. Observe whether one `store-warning` event is emitted with the FR-004 message.

**Expected**: exactly one banner, on the existing `store-warning` channel, saying the saved list may
not reflect the most recent change.

**Actual**: steps 1 and 2 are proven at runtime — `recover_returns_a_usable_guard_after_a_fault_and_reports_it`
and `a_second_recovery_reports_clean_so_no_degraded_mode_accumulates` run against a genuinely poisoned
mutex, and the deliberate panic is visible in [us1-lock.txt](responses/us1-lock.txt). Step 3 is now
proven in two of its three parts and read in the third:

- **The channel and the banner are proven live.** TC-032 made the store unwritable and added a site
  through the running window; the `#banner` element rendered *"Could not write sites.json: Permission
  denied (os error 13)"*. `lock.rs:103` is the crate's only `emit("store-warning", …)` and
  `SharedStore::lock`'s FR-004 warning calls the same private `warn()` helper that produced this
  banner, so the emit → `onStoreWarning` → `#banner` path is no longer taken on trust.
- **The one-shot property is proven** by the second-recovery test.
- **The trigger is still read, not run.** That `recovered == true` calls `warn()` with FR-004's exact
  wording is verified by reading `lock.rs:76–85`.

**Why it cannot be closed by driving the window**: no sequence of clicks poisons a mutex. Closing it
needs an `AppHandle` in a test, which means the `tauri` `test` feature and a mock-app harness — declined
at research time (R7) rather than added for three lines of `emit`.

**Evidence**: `src-tauri/src/lock.rs:76–108` in [messages.txt](responses/messages.txt);
[us1-lock.txt](responses/us1-lock.txt); [gui-09-write-failure.png](screenshots/gui-09-write-failure.png)
**Severity**: Low — declared in advance in `plan.md` and `tasks.md`, not discovered here. The event name
and `{ message }` payload are unchanged, so `src/main.ts`'s `onStoreWarning(showBanner)` needs nothing
new, and that wiring has now been seen working.
