## Summary

**No code changes.** Nothing under `src-tauri/src/` or `src/` differs from what already merged
in PR #4 — `git diff 8feb989..HEAD` over both trees is empty. This PR carries the second staff
review and the second QA run for the already-merged concurrency & robustness hardening feature,
plus a changelog entry recording them.

The substance is that the QA run **closed the feature's longest-standing verification gap**. The
shell layer (`commands.rs`) has no automated coverage by design — a Tauri `State` cannot be
constructed in a unit test without the `tauri` `test` feature, declined at research time (R7) —
and the manual click-through meant to stand in for it had only ever been half-performed: a
*refused* add through the UI, and nothing else. Both `update_site` and `delete_site` dropped an
`app: tauri::AppHandle` parameter in this feature, so "no successful add, no edit, and no delete
has been performed against a running window since the signature change" was a real hole, tracked
as review finding R002 and as the reason tasks T025 and T040 stayed unchecked.

This run drove the real Tauri window through the macOS accessibility API with synthetic mouse
clicks and performed all three, hashing and parsing `sites.json` at every step:

- **Add** — a site typed into the form and submitted. `sites.json` went 3 → 4 with a freshly
  minted UUID, the row appeared, its check ran Pending → Down, no banner.
- **Edit** — the row's Edit button clicked, form populated from the site, label and interval
  changed, Save clicked. Same id, same URL, both fields updated, **still at index 3** — list
  order preserved through a replace.
- **Delete** — the row's Delete button clicked. `sites.json` back to 3, the others untouched and
  in order; the row did not return after a full teardown and relaunch.

A sixth interaction went past the open item. With the app running, the store directory was made
unwritable (`chmod 500`) and a valid non-duplicate site added. The `#banner` rendered *"Could not
write sites.json: Permission denied (os error 13)"*, the row appeared anyway, its check ran to
Down, and `sites.json` on disk stayed byte-identical. That is **FR-011 and US2-AS3 proven at
runtime for the first time** — and because `lock.rs:103` is the crate's only emit of
`store-warning` and `SharedStore::lock`'s FR-004 warning routes through the same private `warn()`
helper, it is also the first runtime proof of the *mechanism* FR-004 reuses.

## Implementation

Nothing new. For the record, the implementation this evidence covers is five Rust files in the
range `2ec8788..8feb989` — `lock.rs` (new, 258 lines), `store.rs`, `commands.rs`, `engine.rs`,
`lib.rs` — and it earns its correctness structurally rather than by test count:

- `SharedStore` exposes **no accessor** for its inner mutex, so an unrecovered lock on the site
  list is *unwritable* outside `lock.rs`.
- `Store::replace` collapses read-decide-write into a single `&mut self` borrow, so FR-013 holds
  because there is no moment to interleave into.
- Recovery is `PoisonError::into_inner()` (preserving what the interrupted operation left behind)
  plus `Mutex::clear_poison()` (making the poison one-shot, so one banner per fault).
