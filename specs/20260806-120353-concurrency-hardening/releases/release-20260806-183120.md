## Two deviations from the standard flow

### 1. No worktree isolation

The run executed in the **primary checkout** (`/Users/clint/src/clintcparker/site-checker`),
which was on `main`. No `worktree_isolation` value was passed into the run, so this is recorded
from observed state rather than from a step's own report. Consistent with the known behaviour that
worktrees are created only at `/speckit.specify`, a resumed or fix-up run reuses the primary
checkout silently.

### 2. A head branch was created, because branch == target == `main`

GitHub cannot open a PR whose head equals its base. Four commits were sitting on local `main`,
unpushed. Options considered:

- **Reset `main` back to `origin/main`** after branching — cleanest history, but mutates the
  user's working state without being asked. Rejected.
- **Push directly to `main`** — bypasses the review the command exists to produce. Rejected.
- **Branch at HEAD without switching, push the branch, open the PR with an explicit `--head`** —
  chosen. Fully non-destructive.

**Working directory was not changed.** The checkout is still on `main`, still at `c5d91d0`, the
same commit the branch points at. Nothing was reset; nothing was force-pushed.

**Consequence to know about**: local `main` already contains these commits, so after the PR merges
a plain `git pull` on `main` will produce a merge commit rather than a fast-forward. Running
`git reset --hard origin/main` on `main` after the merge gives clean history; the commits are
preserved on the branch and on the remote either way.
