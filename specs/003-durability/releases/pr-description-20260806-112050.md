## Summary

`sites.json` is the only file this app owns, and the constitution calls it sacred. Every save
rewrote it in place with a plain `std::fs::write`, which truncates the file and then refills
it. A process that died inside that window — a crash, a force-quit, a dev-server restart —
left a half-written file. The next launch handled that gracefully (empty list, visible
banner, bad file preserved for hand-repair), so it was never *silent* data loss, but the
user's last edit was gone and their whole list was missing until they went and rescued the
file themselves.

This closes that window. Saves are now staged to a fixed-name sibling `sites.json.tmp`,
flushed with `sync_all`, and published with `std::fs::rename` — atomic within a filesystem,
so a reader sees either the complete old file or the complete new one and never a mixture.
Two smaller integrity items from the same roadmap section ride along: a URL scheme now
persists lowercase whatever case it was typed in, and `Store::add` refuses an id it already
holds.

Nothing about what the app *does* changes. What changes is what survives when it stops
unexpectedly. No dependency added, no frontend file touched, no change to the on-disk shape
or the IPC contract.

## Implementation

Two files change. Both are the pure, already-tested core that Constitution Principle IV
reserves for testable logic — `commands.rs`, `engine.rs`, `check.rs`, `lib.rs`, and the
entire frontend are untouched.

### US1 — atomic saves (P1) · `store.rs`

`save` is **split**, not rewritten in place: a private `stage()` does everything except the
rename and hands back the staged path, and `save()` is `stage()` + `fs::rename`. The seam is
the design — it is the only way to prove the guarantee with a deterministic unit test, since
a test can call `stage()` and stop, which *is* the instant "the process died mid-save". The
alternative was racing a killed subprocess.

Decisions worth a reviewer's attention, all recorded in `research.md` and in the code:

- **The staging file is a sibling of `sites.json`, not in `std::env::temp_dir()`.** `rename`
  is only atomic within one filesystem; a temp dir can be on another volume, where the
  rename stops being atomic and usually fails outright.
- **The staging name is fixed (`sites.json.tmp`), not randomized.** A randomized name leaves
  one orphan per crash. A fixed one bounds the artifact at exactly one no matter how many
  saves are interrupted, and the next successful save consumes it.
- **`sync_all` runs before the rename, not after.** The rename publishes the *name*; if the
  bytes are still only in the page cache at that moment, a crash can leave the published
  name pointing at an empty file. This is also why it is `File::create` + `write_all` rather
  than `fs::write` — `fs::write` hands back no handle to sync.
- **Neither failure path cleans up the staging artifact, deliberately.** If staging fails the
  rename never runs and `sites.json` is untouched; if the rename fails the staged copy stays
  as the single permitted orphan. Cleanup would be a second thing to get wrong for no gain.
- **The honest limit, stated in the code rather than glossed:** this defends against the
  *process* dying, because the kernel completes the rename whether or not we survive it. It
  is **not** a power-loss guarantee — macOS `fsync` does not force the drive's own write
  cache the way `F_FULLFSYNC` does, and the parent directory is deliberately not synced.

Because `add`, `update`, and `delete` already funnel through the one private `save`, this
covers every mutation and no caller moved.

### US2 — lowercase scheme (P2) · `model.rs`

`has_leading_scheme` became `leading_scheme_end`, returning the scheme's byte index instead
of a bool, so `normalize_url` lowercases exactly the scheme slice and passes the rest through
verbatim. Switching to `url::Url`'s own serialization would have been the one-liner, but it
would re-introduce the trailing slash that `normalize_url` exists to avoid — `example.com`
must still yield `https://example.com`, not `https://example.com/`.

Only the scheme is touched. Hosts are case-insensitive too, but rewriting them is more of the
user's text than was asked for, and paths and query values are case-*sensitive*. A `HTTP://`
inside a query string is not a leading scheme and is left alone.

**No migration.** `load` does not call `normalize_url`, so a site already stored as `HTTPS://…`
keeps that value until the user next edits it. On that edit it counts as a URL change under
the existing rule, so the row drops to Pending and `method_override` is cleared — one extra
request to re-learn HEAD support, once, for that site.

### US3 — duplicate-id refusal (P3) · `store.rs`

`Store::add` returns `Err` before the push and before the save, so a refusal leaves the
in-memory list and the file agreeing. Pushing first and unwinding on failure would not.

This is **unreachable from the shipped app** — `add_site` mints a fresh v4 UUID per site — and
that is stated plainly rather than sold as a bug fix. Its value is that the store stops
depending on its only caller behaving, which matters the moment an importer or restore path
exists.

### Behaviour change worth knowing about

A **symlink** at the `sites.json` path is now *replaced* rather than followed. A plain write
followed the link and wrote through to its target; an atomic replace cannot. Nothing is
destroyed — the old target keeps every byte it held — but the indirection is gone. This is
inherent to an atomic replace and cannot be avoided without reopening the truncation window
the feature exists to close. The app never creates such a symlink. Verified by experiment,
not recalled (research R5).

Thirteen new Rust tests. The ones that carry the guarantee:

- `an_interrupted_save_leaves_the_previous_list_loadable` — stages, stops, reloads: the old
  list, and **no warning**, so an interrupted save cannot make the live file look corrupt.
- `a_staged_save_holds_the_new_contents_beside_the_live_file` — asserts the staged copy is a
  *sibling*, which is the property the atomicity depends on.
- `a_successful_save_leaves_no_staging_file_behind` — a leftover would mean the rename
  silently became a copy.
- `repeated_staging_never_accumulates_more_than_one_artifact` — three interrupted saves in a
  row. A randomized staging name would leave three orphans here and pass every other test.
- `a_failed_save_leaves_the_previous_file_intact` and
  `a_failed_publish_leaves_the_staged_copy_as_the_single_orphan` — the two halves of the
  failure contract, one failing at staging and one at the rename.
- `a_stale_staging_file_does_not_affect_load_or_the_next_save` — an orphan from a crashed run
  is inert to both.
- `add_rejects_a_duplicate_id` asserts on the **reload**, not the in-memory list, which is
  what proves the refusal preceded any write.
- `lowercases_only_the_scheme` is the guard against a lazy whole-string `to_lowercase()`,
  which would quietly corrupt case-sensitive paths and query values.

The pre-existing `corrupt_file_yields_an_empty_list_a_warning_and_is_left_on_disk` passes
**unmodified** — it is the pin that atomic saves did not replace the graceful-corruption
safety net.
