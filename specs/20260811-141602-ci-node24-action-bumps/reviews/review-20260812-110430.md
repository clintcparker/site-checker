## R001 in detail — why the `ignore:` block matches nothing

The block was introduced at `4adc898` to fix blocker D1 from the fourth review. D1 was correct: the
original `update-types: ["version-update:semver-major"]` form would have silenced these actions
permanently, and the next Node runtime deprecation would arrive as a major the config had pre-emptively
agreed never to mention. The narrow, name-the-declined-version form is the right *design*. The
*syntax* chosen to express it does not work.

GitHub's own [options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)
documents `versions:` as "the standard pattern for the package manager" and gives examples for npm
(`^1.0.0`), Bundler (`~> 2.0`), Docker, NuGet (`7.*`), and Maven (`[1.4,)`). It does not document
`github-actions` — the fifth review noted this and called it the residual risk. The reason it is
absent is that `github-actions` uses a `Gem::Requirement` subclass, which understands Bundler-style
operators and *not* the npm/NuGet `x`/`*` wildcard forms.

Reproduced locally:

```
"8.x"    ->  = 8.x     satisfied_by?(Gem::Version.new("8"))  =>  false
"7.x"    ->  = 7.x     satisfied_by?(Gem::Version.new("7"))  =>  false
"8"      ->  = 8       satisfied_by?(Gem::Version.new("8"))  =>  true
">= 8"   ->  >= 8      satisfied_by?(Gem::Version.new("8"))  =>  true
"7.*"    ->  RAISE Gem::Requirement::BadRequirementError
Gem::Version.correct?("8.x")  =>  true
```

`8.x` is a *legal* `Gem::Version` — RubyGems permits alphabetic segments (`1.0.beta`) — so no error is
raised. It parses cleanly as an equality against a version that will never exist. `7.*` would have
raised and been loud; `8.x` is quiet. The config picked the quiet one.

Note also that `>= 8` would work but reintroduces D1 exactly: it declines every future major forever.
`"8"` is the form that is both parseable and narrow.
