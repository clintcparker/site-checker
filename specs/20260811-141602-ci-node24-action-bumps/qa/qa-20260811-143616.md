## QA Summary

This feature changes GitHub Actions configuration only — fourteen `uses:` pin bumps across `ci.yml` and `release.yml`, one new `.github/dependabot.yml`, and a docs note. It has no runtime surface, so QA ran entirely in CLI mode: YAML parsing, `actionlint`, the repository's own four constitution gates, and — for the acceptance criterion that actually matters — resolving every pinned action tag against GitHub and reading `runs.using` out of its `action.yml` at that exact ref. That last check is the substitute for the real verification surface, which is the GitHub Actions annotation list and has no local equivalent.

**The pins themselves are correct.** All seven distinct actions in the workflows resolve to an existing tag whose `action.yml` declares `runs: using: node24`, every input the workflows pass is still accepted at the target ref, the `upload-artifact@v6` → `download-artifact@v7` → `action-gh-release@v3` artifact round-trip still lands files where the `release` job's globs expect them, and zero `@v4` pins remain. All four constitution gates are green (62 Rust tests, 47 frontend tests, clippy clean, `actionlint` exit 0) — though as no source file changed, that confirms the branch is inert rather than that it fixed anything.

**One scenario fails.** TC-014 checks T018's deliverable — the pinning-convention comment added to the top of `ci.yml`. The comment states that every JS action "sits on the lowest major that runs on node24." Read directly from `action.yml` at each tag, that is false for two of the six bumped actions: `actions/setup-node@v5` and `pnpm/action-setup@v5` are *both already* `node24`, and both are pinned at v6. The branch therefore states something untrue about itself, in the one artifact whose whole job is to explain the choice to the next maintainer. This independently reproduces R001 from the staff review.

Five scenarios (TC-005, TC-011, TC-013, TC-020, and the live half of TC-002/TC-007) are blocked, not skipped: each needs a real GitHub Actions run, a real tag push, or a merge to the default branch. None of them is blocked for want of GUI automation. `specs/20260811-141602-ci-node24-action-bumps/screenshots/` contains `SKIPPED.md`, not a `manifest.json` — the screenshots pass correctly determined this feature has no UI surface and never launched the app, so there is no drivability record to cite and no scenario here that would have needed one.

## Failure Details

### TC-014: The `ci.yml` pinning-convention comment contradicts its own pins

**Status**: ❌ FAIL
**Steps to Reproduce**:
1. Read `.github/workflows/ci.yml:10-11` — "Every JS action here and in release.yml sits on **the lowest major that runs on node24**."
2. For each bumped action, fetch `action.yml` at the major *below* the pin and read `runs.using`:
   `gh api "repos/<owner>/<repo>/contents/action.yml?ref=<major>" --jq .content | base64 -d | grep 'using:'`
3. Compare against the pin actually used.

**Expected**: For all six bumped actions, the major below the pin is `node20` — which would make the pin the lowest `node24` major and the comment true.

**Actual**: Four of six hold; two do not.

| Action | Major below the pin | `runs.using` there | Pinned at | Comment holds? |
|---|---|---|---|---|
| `actions/checkout` | v4 | `node20` | v5 | ✅ |
| `actions/setup-node` | **v5** | **`node24`** | **v6** | ❌ |
| `pnpm/action-setup` | **v5** | **`node24`** | **v6** | ❌ |
| `actions/upload-artifact` | v5 | `node20` | v6 | ✅ |
| `actions/download-artifact` | v6 | `node20` | v7 | ✅ |
| `softprops/action-gh-release` | v2 | `node20` | v3 | ✅ |

Both v6 choices are *correct* — `tasks.md` gives sound reasons for each (setup-node v6 narrows the v5 auto-caching change to npm only, which is a no-op here because both workflows pass `cache: pnpm` explicitly; pnpm/action-setup v6 adds pnpm 11 support). The defect is that the comment records a different rule than the one applied, and `tasks.md` is the only place the real reasoning lives.

**Concrete consequence**: at the next runtime deprecation, a maintainer applying the file's own stated rule literally downgrades `setup-node` and `pnpm/action-setup` to v5 — both still `node24`, so nothing fails, and a deliberate choice is undone with no trace of why. The constitution's Development Workflow section requires that "the code comments record why the tricky parts are the way they are — keep both honest."

**Evidence**: [responses/tc004-lowest-node24-major.txt](responses/tc004-lowest-node24-major.txt)
**Severity**: Medium — no runtime effect; it is a correctness defect in the record, on the one line of the change whose entire purpose is to be the record.
